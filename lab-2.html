1学习产出#

完成本实验后，应当能够：

  1. 运用 L-07 的资源三问（上限由什么决定、如何判断饱和、如何换算容量），为一个服务的 CPU、连接池和磁盘分别建立资源账：先推算上限，再用压测验证。
  2. 搭建一条最小的指标流水线：服务埋点并暴露 /metrics，由 Prometheus 抓取，再用 PromQL 查询。RED 的三条查询和一条 SLI 查询由各组自行编写（L-08 第 19、24、25 页）。
  3. 运用 USE 和 RED 定位瓶颈：区分利用率与饱和度，找出正在排队的资源。该资源可能不在 CPU、内存、带宽这三项常用指标之中（L-07 的引例）。
  4. 对写路径做一次最小改动（组提交）并复测，说明持久性、延迟与吞吐之间的取舍。
  5. 说明一个延迟数值的测量位置与计算方法：客户端还是服务端，平均值还是分位数，以及如何从直方图得出 SLI。

本实验承担模块 5 后半部分的实践：L-06 课程实践计算了“四个上限中哪个最先达到”，L-07 第 22 页预告了“逐项使资源饱和，识别其征兆”，L-08 讲授了 USE、RED、直方图和 SLO。本实验用各组自己测得的数据完整实践一遍。贯穿全程的仍是同一个问题：这项技术解决了什么问题，又增加了什么成本？

实验按“提出假设 → 施加负载或变更 → 收集证据 → 分析 → 改进并复测”的顺序安排：

环节 本实验中的对应内容

2前置知识与环境#

要求熟悉 Linux 命令行，能在多个终端之间切换操作。Go 只需能够编译，不要求编写；建议阅读示例代码，尤其是 internal/metrics/，它是 /metrics 的全部实现。

项 要求（版本查于 2026-10-11）
主机 组内一台 Linux 云主机，至少 2 个 vCPU、2 GB 内存，具有 root 权限。必做部分只使用这一台；第二台仅用于选做 O2。现场检查时需在这台主机上重新运行实验，检查结束前不要释放
磁盘 数据目录 data/ 必须位于真实的块设备上（云盘或本地盘），不能位于 tmpfs。tmpfs 驻留在内存中，fsync 立即返回，写路径的测量将失去意义
系统 命令按 Ubuntu 22.04 或 24.04 编写；其他发行版请替换为相应的包管理命令。WSL2 和容器中可以完成整个流程，但 CPU 和磁盘的数据不能代表真实主机，不得用作正式数据
Go 1.26 或更高版本（实验 1 已安装）。示例没有第三方依赖，构建时无需联网
sysstat 提供 mpstat、iostat、pidstat；vmstat 属于 procps，通常已预装
Prometheus 3.13.4。3.13 是长期支持版（LTS），支持到 2027-07-31
node_exporter 1.12.1
示例 课程模板仓库 https://github.com/zilinglius/operations-2026-lab2-sample（enroll-lab）

本实验只使用统一示例。如需将同样的方法用于小组项目，见选做 O4。

示例服务 enrolld#

enrolld 是一个简化的选课后端，读路径和写路径各含一个可以达到饱和的资源：

接口 功能 对应讲义
GET /api/courses/{id} 先执行一段纯计算（-work，固定循环次数），再从“数据库连接池”中占用一个连接（共 -pool 个连接，每次占用 -db-ms 毫秒） L-06 课程实践的“CPU”和“连接池”两个上限
POST /api/enroll 将一条选课记录追加到 data/enroll.log，按 -sync 指定的方式持久化后才返回“选课成功” L-07 资源账中磁盘 fsync 那一行

“数据库”是模拟的：占用一个连接并休眠 -db-ms 毫秒。它不消耗本机 CPU，只限制可同时执行的查询数量；池满后请求只能排队，这一点与真实连接池相同。真实数据库在连接数增加后自身也会变慢（L-06 第 19 页），这一点无法模拟，见第 9 节。

-sync 有三种取值：

取值 实现方式 类比
each（默认） 每次提交在 write 之后执行一次 fsync，提交之间互斥，同一时刻只处理一次提交 热点行上的锁：锁持有时间中包含等待磁盘的时间（L-07 第 25 页）
group 组提交：后台协程将当前排队的记录一次写入、一次 fsync，再逐个返回 L-07 第 14 页：组提交可合并 fsync
interval 写入页缓存即返回，后台每秒执行一次 fsync MySQL 的 innodb_flush_log_at_trx_commit=2（L-07 第 26、27 页）

3拓扑与测量口径#

必做部分全部在一台主机上完成。loadgen 与 enrolld 绑定到不同的核，以免压测程序与被测服务争用 CPU。Prometheus、node_exporter 与 loadgen 绑定在同一组核上：

vCPU 数 loadgen、Prometheus、node_exporter（GEN_CPUS） enrolld
2 0 1
4 0-1 2-3
8 及以上 0-3 4-5

enrolld 最多分配 2 个核，否则其上限过高，loadgen 无法以足够的速率发送请求。分核前先查看 lscpu -e：CORE 列相同的两个 CPU 是同一物理核上的两个超线程，应尽量使 loadgen 与 enrolld 位于不同的 CORE。许多 2 vCPU 云主机就是一个物理核的两个超线程，此时无法分开，如实记录即可（L-07 第 9 页：1 个 vCPU 通常对应一个超线程）；也有虚拟机不暴露这一层信息，lscpu -e 中每个 vCPU 各占一个 CORE，此时同样如实记录。

口径#

指标 测量位置 计算方法
到达率 loadgen 每个阶段按目标到达率发送请求。开环：按计划时刻发送，不等待前一个请求返回；间隔服从指数分布（泊松到达），模拟相互独立的用户
吞吐 ok_rps loadgen 该阶段成功（2xx）的请求数 ÷ 阶段时长
错误率 error_rate loadgen （非 2xx + 超时 + 连接错误）÷ 发出的请求数。服务端的 server_error_rate 只统计 5xx
客户端延迟 loadgen 只统计成功的请求，从计划发送时刻计时至读完响应体为止。分位数采用最近秩法：排序后取第 ⌈p% × n⌉ 个
服务端耗时 enrolld 的直方图 从进入处理函数到处理函数返回，不含内核中的排队与网络传输，也不含请求进入处理函数之前在 Go 运行时中的等待时间
服务端 p99 PromQL histogram_quantile 在桶内做线性插值，精度受桶宽限制（L-08 第 10 页）
每请求 CPU Prometheus 进程 CPU 秒数的增量 ÷ 请求数的增量
阶段窗口 promsteps 每个阶段去掉开头 5 秒。Prometheus 每秒抓取一次 enrolld、每 5 秒抓取一次 node_exporter，因此一个 30 秒的阶段中，inflight_avg 等瞬时值约有 25 个样本

Little's Law（L = λ × W）中的 W 是平均时间，必须使用平均值，不能代入 p99；各阶段、各实例的分位数也不能直接平均（L-08 第 10、13 页）。

为什么采用开环：wrk 等闭环工具固定 N 个连接，收到响应后才发送下一个请求，服务一旦变慢便自动减少发送，排队因此被掩盖，测得的延迟偏乐观。开环更接近选课开放时彼此独立涌入的学生。代价是压测程序必须按时发出请求，因此 loadgen 也报告自身的发送滞后（lag_p99_ms）和 CPU（gen_cpu_pct），超出阈值时在 warn 列中给出警告。

每次实验产出的数据#

scripts/run.sh <名字> <loadgen 参数…> 运行一次实验，结果全部存入 runs/<名字>/。名字不能重复；重新运行同一实验时换一个名字，两次的数据均保留：

文件 内容
meta.txt 主机、内核、磁盘、enrolld 的参数（/config）、绑核、压测命令、仓库提交
steps.csv 客户端数据，每个阶段一行；最后一行 all 是所有有负载阶段的合计
red.csv 服务层数据，每个阶段一行，查询见 deploy/queries-red.txt
use.csv 资源层数据，每个阶段一行，查询见 deploy/queries-use.txt
vmstat.log、mpstat.log、iostat.log、pidstat.log 资源层的原始输出，每秒一行
metrics-start.txt、metrics-end.txt 开始和结束时 /metrics 的原文

各列的含义见两个查询文件中的注释。按 USE 和 RED 分类如下：

对象 U 利用率 S 饱和度 E 错误
CPU svc_cpu_busy、cpu_cores 内核：procs_running_avg、cpu_psi_some、cpu_wait_threads；Go 运行时：sched_wait_p99_ms —
连接池 pool_in_use_avg ÷ 池大小 pool_wait_p99_ms 等连接超时返回 503
磁盘 disk_util、disk_w_per_s、disk_wkb_per_s disk_aqu_sz、disk_w_await_ms、disk_f_await_ms、cpu_iowait 写入失败返回 500
内存 mem_available_min_mb swap_in_per_s OOM（留待实验 3）
服务（RED） R：server_rps、ok_rps 等待对象：inflight_avg、pool_wait_p99_ms、sched_wait_p99_ms E：server_error_rate、error_rate；D：server_p99_ms、p99_ms

提示
  • promsteps 报告“返回了 N 条序列”，说明查询未聚合，应用 sum(...) 将多条序列合并为一条。直方图须先 sum by (le) 再计算分位数，因为直方图还带有 code 标签。

任务 2：读路径，连接池与 CPU 哪个先达到上限约 120 分钟#

这正是 L-06 课程实践的“四个上限中哪个最先达到”，只是数据须使用本组的实测值。

  1. 先预测，再测量。 用任务 1 测得的每次查询占用时间和每请求 CPU，按 L-06 第 16、19 页的换算方法计算两个上限：连接池上限为“池大小 ÷ 每次占用的秒数”，CPU 上限为“enrolld 的核数 ÷ 每个请求的 CPU 秒数”。写下哪个上限先达到、客户端 p99 从多少请求/秒起会超过 50 ms，填入 LAB2.md 第 4.1 节，然后再开始测量。预测写好后不要修改：预测错误不扣分，与实测不一致之处正是分析需要讨论的内容。

  2. R1：默认的 -pool 4。 以较小的上限为基准生成到达率（默认取 0.2～1.2 倍，共 9 个阶段，约 5 分钟），运行一次：

    运行期间可以另开一个终端观察 vmstat -w 1，或在 Prometheus 界面中绘制 db_pool_in_use 和 http_inflight_requests。

  3. CPU 消耗在何处。 在约 0.8 倍上限的负载下采集 20 秒 CPU 剖析：

    main.spin 是读路径上的计算。其余时间消耗在 HTTP 处理、系统调用和 Go 运行时上，这些同样计入“每个请求的 CPU”。

  4. R2：调大连接池，观察下一个达到上限的资源（L-06 课程实践讨论 1）。从 R1 中选取一个尚未达到上限、负载又尽可能高的阶段，用其 cpu_ms_per_req 重新推算 CPU 上限 C。将连接池调至 P2 = ⌈2 × C × 每次查询的秒数⌉，使连接池上限为 CPU 上限的两倍，这样先达到上限的应当是 CPU。将 C、P2、到达率和预测写入 LAB2.md 第 4.4 节。然后在终端 A 按 Ctrl-C 停止 enrolld，用新的池大小重启：

    服务过载后，loadgen 若在某个阶段结束时发现成功返回的请求不足一半，便停止后续阶段，以免拖垮主机。这在 R2 末尾属于正常现象，记录停止于哪个阶段即可。如果直到最后一个阶段仍未达到上限，说明 C 估计偏低：用最后几个阶段的 cpu_ms_per_req 重新估计 C，换一个名字重新运行，两次的数据均保留。

检查点

第 4.1、4.4 节已写预测；R1 的阶段超过了连接池上限，R2 的阶段超过了 CPU 上限；runs/r1-pool4/pprof-top.txt 存在；LAB2.md 第 4 节的表格都已粘贴。

任务 3：写路径与磁盘约 90 分钟#

写路径的服务端耗时通常只有几毫秒，因此 SLO 阈值改为 20 ms（export SLO=0.02；之后若回到读路径重新运行，先执行 unset SLO，恢复默认的 50 ms）。每次重启 enrolld 之前删除上一次的 data/enroll.log，该文件会持续增大。

5选做#

选做不影响必做部分的评分，仅用于加分，上限见第 7 节。每项都须先写下预期，再进行测量。

  • O1 内存与 GC：GET /api/report?mb=4 每个请求分配 4 MB 临时内存。在同一到达率（例如 100 请求/秒）下分别运行 GOGC=100 和 GOGC=400（启动 enrolld 时设置环境变量，例如 GOGC=400 taskset -c 1 bin/enrolld），比较 go_gc_cycles_total、go_gc_cpu_seconds_total 的增量、process_resident_memory_bytes 和 p99。说明其中以什么代价换取了什么，并联系 L-06 第 12 页 JVM 的堆与 GC。
  • O2 网络：需要第二台主机，两台位于同一 VPC。主机 A 用 -addr 0.0.0.0:8080 启动 enrolld，安全组只对主机 B 的内网地址放通 8080；在主机 B 上用 loadgen 请求 /api/export?kb=256，逐步加压。在主机 A 上用 sar -n DEV 1 观察 txkB/s，用 ss -tin 观察重传，按 L-07 第 19 页计算带宽需求，找出该主机的带宽上限。run.sh 要求 loadgen 与 enrolld 在同一台主机上，因此 O2 请直接运行 loadgen，并在主机 A 上自行记录 sar 的输出。完成后关闭放通的端口。
  • O3 告警与看板：为读路径的 SLO 编写一条基于燃烧率的 Prometheus 告警规则（L-08 第 21 页），放在 deploy/rules.yml，并在 prometheus.yml 中用 rule_files 引用；通过一次过载使其触发，从 /api/v1/alerts 获取触发记录。再按 L-08 第 29 页的“三行九格”，在 Prometheus 界面或 Grafana 中为 enrolld 搭建一张看板，说明每一格使用的查询。
  • O4 迁移到小组项目：为本组的项目加入 RED 三项指标（可参考 internal/metrics/），测出一种资源的上限，按 L-07 的格式写一行资源账。

9测量与局限#

  • 单机模式：loadgen 与 enrolld 共享内核、内存带宽和末级缓存，绑核只能减少二者对 CPU 的争用。请求经回环地址发送，不经过网卡，因此网络开销被低估；网络方面的结论需依靠 O2。
  • 云主机的 CPU 和磁盘都受邻居干扰。同一台主机在不同时间测量，相差 10% 以上很常见。需要比较的两次实验应连续进行，结论中写明测量所用的主机。
  • 每请求 CPU 不是常数。低负载时，运行时唤醒、缓存失效和 CPU 节能状态的开销分摊到少数请求上，因此单个请求的开销显得更高。用低负载数据推算上限会偏保守，问题 1 需讨论这一点。
  • 30 秒的阶段在 50 请求/秒时只有 1500 个样本，p99 仅取决于最慢的 15 个请求，因此低速率阶段的 p99 噪声很大。
  • 服务端 p99 由直方图插值得到，精度受桶宽限制；inflight_avg、pool_in_use_avg 是每秒采样一次后取平均，一个阶段约 25 个样本，仍存在抽样误差，在途数较小时尤为明显。
  • 客户端延迟从计划发送时刻算起，包含约 1 ms 的发送滞后（见 lag_p99_ms）。
  • 模拟数据库只模拟“占用连接的时间”，不模拟数据库自身的 CPU、锁和 I/O。在真实系统中，连接池调大后数据库会变慢（L-06 第 19 页），本实验观察不到这一现象。
  • fsync 耗时取决于磁盘类型与规格、文件系统和挂载参数。云盘性能通常与容量、规格挂钩。
  • enrolld 用 Go 编写：GOMAXPROCS 跟随绑核数，CPU 不足时排队发生在 Go 运行时中。若换成 Java 或 Node.js，CPU 饱和在内核指标上的表现会有所不同（L-06 第 13、14 页）。
